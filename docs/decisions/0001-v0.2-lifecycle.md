  Issue #6 asks for product review before shipping; the operator delegated these calls for

## Decisions (SPEC-v0.2 §2, recorded verbatim)

Section references (§3, §5, §8.1) point to SPEC-v0.2, the v0.2 build contract kept with
the release records; in this repository the same rules are in [lifecycle.md](../lifecycle.md).
The storage migration that carries these decisions is schema **v4** (v3 is the earlier
additive `review_repairs` table).

Record these verbatim in `docs/decisions/0001-v0.2-lifecycle.md`. Each is a default in ruleset `lifecycle-v1` (§3). Issue #6 asks for product review before shipping; the operator delegated these calls for this run and will not answer mid-run, so the ADR records them as **delegated defaults for a private testing prerelease**, each one changeable in a later ruleset version without migrating existing lives backwards.

The three **confirmed** requirements are honoured:
- evolution is tied to XP and levels;
- neglect can permanently end a life;
- a replacement starts at level 1.

| # | Question (issue #6) | Decision | Rationale |
|---|---|---|---|
| D1 | Is permadeath the default or opt-in? What happens on migration? | Two modes per life. **`permadeath`** (the issue's "Hardcore") is **preselected** on every rules card and adoption form. **`gentle`** (the issue's "Standard"): when grace runs out the pet *faints* and Start stays blocked until care; it never dies. A life's clock is **unarmed** until the user explicitly acknowledges the rules (`pet.rules`, or `acknowledge_rules` inside `pet.adopt`). While unarmed there is no decay, no neglect and no countdown, so behaviour matches v0.1. **Migration and first run create life #1 unarmed**: no retroactive loss and no backdated neglect. Switching permadeath→gentle is allowed at any time while the pet is alive and not `death_pending`. Switching gentle→permadeath requires `healthy`. Both switches are journaled. | Permadeath is the requested mechanic, so it is the default rather than a buried opt-in (judge concern about Design 0). Arming by explicit acknowledgement meets the humane rule "describe the full rules before enabling". A gentle detour cannot dodge death: neglect keeps accruing in gentle, and switching back requires full recovery to healthy. |
| D2 | Which needs are lethal? Thresholds? Recovery? | **Lethal needs: hunger and thirst only.** Mood (`mental_health`) and hygiene produce warnings only. Bathroom-due and nap-due block Start (unchanged) and are never neglect. Thresholds are in §3. Recovery: the *matching* care action (or a routine step that fills that need) sets the meter to 100, starts that need's satiety hold and resets that need's neglect to 0. An unrelated action changes nothing else. Critical clears only when no lethal need remains at or beyond `critical_after`. | This is the issue's humane baseline. Zero-meter conditions caused by normal work debits cannot cause neglect: Start requires full meters, and decay is discarded while a task holds the slot. |
| D3 | Clock, pause and travel | Only **observed attended time** counts (§5): CodePet bar widget loaded, user not idle for 180 s, no focused fullscreen workspace, life alive, armed, not paused, not sleeping, no slot task, not `death_pending`. Time arrives as 60 s ticks; a tick is credited only when its wall gap is 50 to 90 s, and only after 180 s of continued activity (idle look-back). Rust caps credit by CLOCK_BOOTTIME elapsed since the last settlement. There is no offline or overnight catch-up and at most 8 h of credit per settlement. **Pause/Travel** (the existing `pet.pause`, stored in `pet_state.decay_paused`) is explicit, durable and visible, and is available in any living state including critical. It freezes decay, neglect and grace, grants nothing, refills nothing, and does **not** block care or Start. Resuming restores nothing. | This is the issue's recommended baseline, made robust against clock jumps. Under every uncertainty it under-charges. |
| D4 | Stage count, XP boundaries, reversal, rollout | **3 stages for every species:** young (level 1, 0 XP), grown (**level 2, 80 XP = 4 accepted mock tasks**), mature (**level 4, 400 XP = 20 accepted mock tasks**). The level curve stays `[0,80,200,400,700]` (levels 1 to 5, unchanged from #3). Stage thresholds are ruleset values with a per-species override map (empty in v1). Stage is **derived from the life's current authoritative XP**. Evolution journal rows are history and never re-celebrate. A reversal lowers the derived stage and keeps the journal; v0.2.0 has no reversal path, so this is tested by fixture. **All 15 species × 3 stages ship in v0.2.0.** The operator goal overrides the issue's three-species phase 1. | The first evolution comes early enough to be felt and tested, and the curve is unchanged, so `xp_view` output is identical for existing data. |
| D5 | Lock species per life, or allow switching? | **Cosmetic appearance switching within a life** (issue #5's shared-state model). `lives.species` is the species at adoption and never changes. `lives.appearance` is `selectedPetId`. XP, meters, holds, neglect, grace, sleep and slot are shared by the life. All 15 appearances are available from the start, and levels unlock nothing functional. Account-level lifetime XP and mastery never seed a new life. | Matches #5. It cannot be used to dodge neglect, because there is one record. |
| D6 | Race ordering | Every write transaction runs the fixed order **settle presence → settle sleep → command body → `finalize_if_due` → `state_version++` → commit** (§8.1). XP goes to `tasks.life_id`, set at Start and backfilled in migration. Time is discarded while a task holds the slot, so death cannot become due during a task. If a death is still due with the slot occupied (defensive, for example a restored DB), the life becomes `death_pending`: Start is blocked; review, accept, discard, cancel and recover stay available; and death finalizes in the transaction that frees the slot, **after** any XP from that transaction. | Exactly-once and crash-safe, with one helper on every path. |
| D7 | Humane guarantees (added) | (a) The settlement that **enters** critical discards the rest of its credited interval, so death can never happen in that same settlement, and critical is always visible in at least one committed state before grace runs. (b) Grace is **frozen at critical entry**. (c) Per-life settings can only become **more lenient** (longer grace or critical_after, slower decay); a stricter request is refused. Pace is chosen at adoption only. (d) Corrupt, missing or uncertain time input is ignored and never kills. (e) Copy is calm: no streaks, guilt, sounds, flashing or notifications. Every duration is labelled "active time". UI predictions never show a death. | Satisfies "cannot silently shorten an existing safe window" by construction. |
| D8 | First life and adoption | Migration creates **life #1: cat "Ginger"** (`origin` is `migrated` if any task or demo XP exists, otherwise `first_run`). All historic tasks and demo XP rows attach to it, so current XP and level survive. Adoption (`pet.adopt`) is explicit, requires no living or pending life and a free slot, and must include the rules acknowledgement and a mode. The new life starts at **level 1, 0 XP, young stage**, with meters at **70.00**, holds 0, neglect 0, rest and bathroom counters 0, no sleep, and `welcome_care_available = 1` (one free routine). A durable "no living companion" state is valid. Adoption is never automatic. | Starter care is generous but still needs one routine before the first Start, as #3 already requires. |
| D9 | Retirement | `pet.retire {life_id, confirm_name}` is voluntary, terminal and journaled with a memorial. It requires the typed name to match, a free slot, not critical and not `death_pending`. It is never used for neglect. | Retirement cannot launder a pending death. |
| D10 | Pace presets | **`steady`** (default) and **`playtest`** (opt-in, adoption-only, badged "Playtest" everywhere). Playtest uses 20× decay, short windows and the same level curve. The migrated life is `steady`. | Lets the operator walk warning, critical, death and adoption in under an hour without touching real thresholds. |
| D11 | Celebration dedupe | `life_events(kind='evolved')` is unique per `(life_id, stage)` and carries a durable `seen_at_ms`. The UI that performed the acceptance celebrates from its response, then sends `pet.events_seen`. Other UIs show a static "★ grew" badge and celebrate on the user's next explicit interaction (popup open, or a click on the pet), then send `pet.events_seen`. A restart never replays a celebration. | Durable, and needs no file-event RPC. |
| D12 | Notifications | None in v0.2.0. Status appears only as bar badges and in-card text. | Issue #6 tone rules. |
